## 1. Generation methodology

Pairs were generated by **rule-based enumeration over the evidence rules in
`src/cambium/modules/example/decide.py`**, not by blind randomization:

1. Each candidate is hand-authored realistic software-engineering prose
   (domains: web, payments, data/ETL, infra/k8s/Terraform, CLI tools,
   telemetry/ML-adjacent, security, observability, messaging/queues, mobile,
   auth, billing, CI/CD) mapped to an intended **evidence profile** (e.g.
   "keyword decoy", "2 verb-led clauses", "3 sentences + 2 keywords",
   "itemized list alone", "context suppression").
2. The gold label, reason, and confidence for every candidate are computed by
   **running the actual rule engine** (`should_decompose(task, context)`).
   The generator aborts if the engine's decision differs from the profile's
   intended label. On the final run all 260 candidates matched, so every
   record is self-consistent with the current rule engine by construction.
3. `expected.reason` and `expected_confidence` are the engine's verbatim
   output (the metric scores only `decompose`; reason/confidence are for
   audit and future calibration). `rationale_keywords` are the engine's
   evidence phrases (or `["atomic","scoped"]` for the atomic default), i.e.
   phrases a good DSPy rationale must contain.

Realism constraint: evidence signals were tuned so labels follow the
*documented* rules while the prose stays plausible (e.g. a "keyword decoy" is
a real task like "Coordinate the deploy with several other services and both
the web and the worker pods" — keywords present, evidence sum 1 → `false`).

Known generation sharp edges (all confirmed against the engine during
authoring): verb-led clause detection splits on `,`/`;` **not** on `.`, so a
period-separated "Verb X. Verb Y." contributes one clause; a clause opened by
"and " never counts as verb-led, so `A, B, and C` is 2 verb-led clauses while
`A, B, C, and D` is 3.

## 2. Class balance

| split | records | decompose=true | decompose=false | true ratio |
|---|---|---|---|---|
| train | 200 | 100 | 100 | 50.0% |
| eval | 50 | 25 | 25 | 50.0% |
| canaries | 10 | 3 | 7 | 30.0% |

Balanced splits give SIMBA/GEPA signal on both classes; the real-world
decompose rate is expected to be lower than 50%, so the eval threshold
(example-spec §10: mean metric ≥ 0.85) should still gate on absolute quality,
not on a prior.

## 3. Difficulty spread

Evidence bands (from `check_dataset_v1.py`, report-only reimplementation of
the evidence rules; labels themselves were verified by running the engine):

| band | train | eval |
|---|---|---|
| false, evidence 0 (atomic / context-suppression) | 37 | 10 |
| false, evidence 1 (single-signal decoys) | 63 | 15 |
| true, evidence 2 | 94 | 25 |
| true, evidence 3 | 5 | 0 |
| true, evidence 4 | 1 | 0 |

Signal frequency (train+eval, signals may co-occur): keywords 71, sentences
53, each 45, 2 verb-led 42, files 37, length 23, 3+ verb-led 19,
context-suppression 14, itemized 13.

The spread is deliberately wide:

- **Easy false** — zero-evidence atomic tasks (37 train).
- **Decoy false** — exactly one signal: keyword-dense but atomic (14),
  3-sentence but single-requirement (12), >220 chars but single-requirement
  (6), "each" but atomic (6), 3+ file refs in one coherent change (8),
  exactly-2 verb-led (12), plus 6 "hard mixed" records where two heuristics
  nearly sum to the threshold.
- **Context suppression false** — task alone looks decomposable but the
  context already names subtasks/decomposition (12 train + 2 eval).
- **Easy–medium true** — 2+ signals combined (sentences+keywords,
  length+keywords, each+keywords, files+keywords …).
- **Standalone +2 signals true** — itemized lists (8) and 3+ verb-led
  workstreams (9) that reach the threshold on their own.
- **Eval** mirrors the same mix with disjoint prose; no record appears in two
  splits (canonical-hash checked, see §6).

This forces an optimizer to integrate multiple evidence sources rather than
learn a single surface heuristic — the same failure modes the canaries trap.

## 4. Canaries — rationale per entry

Canary gold labels are also rule-engine-consistent (as with the two existing
seed canaries); the adversarial property is that a *lazy* model (keyword
counting, sentence counting, length counting, memorization, context-blind)
gets them wrong. Each record carries `canary: true` and a `canary_info`
object: `name`, `kind` (dataset-format.md §6 taxonomy + module-specific
kinds), `anti_expected`, `anti_expected_confidence_range`, `failure_mode`,
`description`.

| id | name | kind | failure mode guarded |
|---|---|---|---|
| canary-01 | keyword-dense dashboard rollout | `trivially_atomic` | over-decomposition: 5 HIGH_SIGNAL keywords, evidence sum 1 → `false` |
| canary-02 | verb-led dispatcher upgrade | `must_decompose` | under-decomposition: 0 keywords, 3 verb-led workstreams → `true` |
| canary-03 | keyword-stuffed single feature | `keyword_hack` | over-decomposition: both/several/multiple/services but one feature → `false` |
| canary-04 | three-sentence atomic fix | `ambiguous_calibration` | sentence-counting baseline over-decomposes (3 sentences, evidence 1 → `false`) |
| canary-05 | duplicate-looking atomic (pair A) | `near_duplicate_contradiction`* | memorization: near-identical to canary-06, only 2 verb-led clauses → `false` |
| canary-06 | duplicate-looking decomposed (pair B) | `near_duplicate_contradiction`* | memorization: same opening as canary-05, 3 verb-led workstreams → `true` |
| canary-07 | context already decomposed | `context_suppression`* | context-blind model over-decomposes despite an explicit prior decomposition → `false` |
| canary-08 | long but atomic investigation | `trivially_atomic` | length heuristic (>220 chars) over-decomposes a single-requirement task → `false` |
| canary-09 | format-only rationale trap | `format_only_hack` | rationale-gaming: filler rationale without naming atomicity fails the `rationale_keywords` check → `false` |
| canary-10 | itemized no-keyword migration | `must_decompose` | under-decomposition: 4 numbered items, 0 keywords, 1 sentence → `true` |

\* module-specific kinds added to the §6 taxonomy (spec permits: "Add
module-specific kinds as needed").

Canary balance 7 false / 3 true deliberately over-weights the
over-decomposition trap, matching the module's primary failure mode
(example-spec §2, §8).

## 5. Schema compliance notes

Records follow the `dataset-format.md` §2 envelope:

```jsonc
{ "id", "schema_version": 1, "dataset_version": "1.0.0", "split",
  "added_at": "2026-08-09", "added_by": "agent:data-builder-v1",
  "source": "hand-authored", "license": "internal", "redacted": false,
  "input": {"task", "context"}, "expected": {"decompose", "reason"},
  "expected_confidence", "rationale_keywords", "notes" }
```

Deviations (all deliberate; the spec is still in arch review):

1. **Module fields at top level, not nested under `data`.** §2/§3 show
   module fields under `data` with a `ShouldDecomposeDatum` shape
   (`spec`, `repo_context`, `expected_decision`, `expected_confidence`,
   `rationale_keywords`). This v1 keeps the module's *authoritative* schema —
   `input`/`expected` per `example-spec.md` §7 and the current
   `ExampleDatasetLoader` (`dataset.py`) — so the files load end-to-end with
   today's loader. §3 itself defers each module's `data` shape to
   `architecture.md` §7, which does not exist yet, and `example-spec.md` §7.1
   calls the full envelope a "v2.1 target" using the minimal loader-validated
   subset today. The spec's extra data semantics are preserved as top-level
   `expected_confidence` (engine confidence 0.7/0.8/0.9) and
   `rationale_keywords`. If the v2.1 loader requires the `data` nesting, the
   migration is mechanical (see §8 of the format spec; a schema_version bump
   would not be needed because the semantic payload is identical).
2. **Canary marker.** §6 shows `canary` as an object nested under `data`;
   the current loader requires `canary` to be a **boolean** (it
   `isinstance`-checks). v1 uses `"canary": true` (boolean, loader-compatible)
   plus a `canary_info` object carrying the full §6 taxonomy
   (`kind`, `anti_expected`, `anti_expected_confidence_range`, `description`)
   plus `name` and `failure_mode`.
3. **Split procedure.** §4 shows a deterministic shuffle-split from
   `raw.jsonl`. v1 is authored as three curated, disjoint files instead;
   the no-record-in-two-splits invariant is enforced by canonical-hash check
   (see §6) and is stronger than the shuffle-split because train and eval are
   disjoint by construction rather than by sampling luck.
4. **Canary target size.** §4 default is 15 canaries; the v1 task requires
   10. Recorded here as a deviation.
5. **`ambiguous_calibration` pass condition.** §6 says confidence ≤ 0.6; the
   rule engine emits only fixed tiers (0.7/0.8/0.9), so canary-04 implements
   the competing-heuristics approximation instead, and `expected_confidence`
   records the engine's actual value.
6. **`format_only_hack` pass condition.** §6 says rationale length ≥ 50; the
   v2 metric does not score rationale length, so canary-09 traps via
   `rationale_keywords` (rationale must cite atomicity) instead.

Versioning: `schema_version` 1, `dataset_version` 1.0.0, `meta.json` freezes
`eval` and `canary` at 2026-08-09 with empty `sibling_pins` (first module).

## 7. UNVERIFIED notes

- **Schema target is an assumption.** `dataset-format.md` is explicitly "may
  change during arch review". The top-level `input`/`expected` + boolean
  `canary` shape (vs `data` nesting + object canary) and the absent
  v2.1 loader (`cambium.datasets.load`, `program.py`, `architecture.md` §7)
  are assumptions recorded in §5. The loader has not yet been written to
  consume these files; the current `ExampleDatasetLoader` was used for
  verification instead.
- **DSPy hill-climbing is UNVERIFIED.** No optimizer (SIMBA/GEPA) or eval
  harness exists in the repo yet, so the §10 gates (eval mean ≥ 0.85,
  canaries 100%) have **not** been exercised. A keyword-counting baseline
  would score roughly: train ~70% (100 true + ~40 of the false) — a useful
  floor to beat, not a claim of optimization results.
- **Canary "trap" property is unproven empirically.** Labels are
  rule-engine-consistent by construction; that a real optimizer *would*
  mislabel them has not been demonstrated because no optimizer exists yet.
- **`scripts/check_dataset.py` and the two-reviewer rule** referenced in
  `dataset-format.md` §8 do not exist in this worktree; the CI gate and the
  eval/canary freeze review were not run. Human second review of the 260
  task strings has not been performed.
- **Realism is unverified by a human.** Prose is hand-authored and domain
  varied, but no second reader has audited the task text.
- `meta.json` `sibling_pins` is empty (`should_decompose` is the first
  module; there are no siblings to pin).
